# AudioWRT Architecture

## Overview

AudioWRT is a reproducible downstream build definition, not an OpenWrt fork.

The repository contains only AudioWRT-owned build policy and image content. The OpenWrt source tree is cloned at build time and remains the source of truth for hardware support.

```text
AudioWRT repository
        |
        | build inputs
        |-- PLATFORM
        |-- OPENWRT_REF
        v
Clean OpenWrt checkout
        |
        | OpenWrt target metadata
        v
Selected device profile
        |
        |-- hardware packages from OpenWrt
        |-- AudioWRT packages added
        |-- router packages removed
        |-- AudioWRT filesystem overlay
        v
AudioWRT firmware
```

## Platform ownership

AudioWRT does not maintain a platform database.

`PLATFORM` is the OpenWrt device profile identifier supplied at build time. AudioWRT generates OpenWrt target metadata and resolves that profile to its target and subtarget.

This keeps device-specific knowledge where it belongs:

- board definitions: OpenWrt;
- kernel and device tree: OpenWrt;
- Wi-Fi firmware and drivers: OpenWrt;
- Ethernet and switch drivers: OpenWrt;
- USB host controller packages: OpenWrt;
- generic audio-appliance policy: AudioWRT.

## USB capability gate

USB host capability is mandatory in the initial architecture.

The validator runs before AudioWRT packages are added. It examines `Target-Profile-Packages` generated by OpenWrt for the selected device and requires at least one recognized USB host package from `config/usb-host-packages`.

The validator intentionally uses the cloned OpenWrt source as its source of truth instead of querying the OpenWrt website. This guarantees that capability validation corresponds to the exact OpenWrt ref being built.

Validation states are deliberately strict:

```text
USB confirmed -> continue
USB missing   -> fail
USB unknown   -> fail
```

A false negative is preferable to producing an AudioWRT image for hardware whose required audio-output path cannot be confirmed.

## Package policy

The effective firmware package set is conceptually:

```text
OpenWrt device defaults
+ OpenWrt device profile packages
+ AudioWRT required packages
- AudioWRT forbidden router packages
```

AudioWRT never replaces device-specific packages with its own model definitions.

The package policy is stored in:

- `config/packages.add`
- `config/packages.remove`

After OpenWrt resolves the configuration, AudioWRT verifies that every required package is built into the firmware and every forbidden package is absent. Dependency conflicts therefore fail the build instead of silently changing the product definition.

## Filesystem overlay

`files/` is copied to OpenWrt's root filesystem overlay before compilation.

It is reserved for distribution-level defaults and identity. Reusable runtime functionality belongs in `audiowrt-packages` whenever possible.

## Package feed

`audiowrt-packages` is added as an OpenWrt feed during every build:

```text
src-git audiowrt https://github.com/demonccc/audiowrt-packages.git
```

This keeps the distribution and reusable OpenWrt packages independent.

## OpenWrt version model

OpenWrt versions are build inputs rather than AudioWRT branches.

`OPENWRT_REF=stable` resolves to the latest final upstream release tag. An explicit branch, tag or commit can be supplied for testing or maintenance.

Every output includes a manifest recording the exact OpenWrt commit, AudioWRT commit and AudioWRT package-feed commit used by the build.

## Runtime direction

AudioWRT is a network audio appliance rather than a general-purpose router.

The intended runtime networking model is:

- Ethernet as a DHCP client;
- Wi-Fi as a station/client after provisioning;
- a minimal temporary AP for first-boot provisioning;
- no normal NAT or router role;
- mDNS for local discovery;
- a reduced LuCI experience focused on Audio, Network and essential System functions.

Provisioning and the final LuCI information architecture are separate runtime milestones and are not hard-coded into the build resolver.
