# AudioWRT Architecture

## Overview

AudioWRT is a reproducible downstream build definition, not an OpenWrt fork.

The distribution repository contains build policy and image-level content. OpenWrt is cloned at build time and remains the source of truth for hardware support. Reusable runtime behavior is implemented in `audiowrt-packages`.

```text
AudioWRT repository
        |
        | build inputs
        |-- PLATFORM
        |-- OPENWRT_REF
        |-- AUDIOWRT_PACKAGES_REF
        v
Clean OpenWrt checkout
        |
        | OpenWrt target metadata
        v
Selected device profile
        |
        |-- hardware packages from OpenWrt
        |-- AudioWRT packages added
        |-- router packages removed
        |-- small distribution overlay
        v
AudioWRT firmware
```

## Platform ownership

AudioWRT does not maintain a platform database.

`PLATFORM` is the OpenWrt device profile identifier supplied at build time. AudioWRT generates OpenWrt target metadata and resolves that profile to its target and subtarget.

Device-specific knowledge stays in OpenWrt:

- board definitions;
- kernel and device tree;
- Wi-Fi firmware and drivers;
- Ethernet and switch drivers;
- USB host controller packages.

AudioWRT owns only generic appliance policy and runtime behavior.

## USB capability gate

USB host capability is mandatory in the initial architecture.

The validator runs before AudioWRT packages are added. It examines `Target-Profile-Packages` generated by OpenWrt for the selected device and requires at least one recognized USB host package from `config/usb-host-packages`.

Validation is deliberately strict:

```text
USB confirmed -> continue
USB missing   -> fail
USB unknown   -> fail
```

A false negative is preferable to producing an AudioWRT image for hardware whose required audio-output path cannot be confirmed.

## Package policy

The effective firmware package set is conceptually:

```text
OpenWrt device defaults
+ OpenWrt device profile packages
+ AudioWRT required packages
- AudioWRT forbidden router packages
```

The policy lives in:

- `config/packages.add`
- `config/packages.remove`

After OpenWrt resolves the configuration, AudioWRT verifies that every required package is built in and every forbidden router package is absent.

## Runtime package ownership

Reusable appliance behavior belongs in `audiowrt-packages`.

The MVP package split is:

```text
audiowrt-core
  -> device identity
  -> Ethernet client defaults
  -> first-boot Wi-Fi setup AP
  -> setup web UI
  -> STA provisioning and rollback
  -> explicit WPS-button recovery
  -> IP forwarding disabled

audiowrt-usb-audio
  -> USB Audio Class dependency
  -> USB DAC discovery
  -> ALSA default output
  -> USB hotplug handling

audiowrt-mpd
  -> MPD configuration
  -> /mnt/music
  -> HTTP/local playback
  -> AudioWRT ALSA output

audiowrt-airplay
  -> Shairport Sync configuration
  -> AudioWRT device identity
  -> AudioWRT ALSA output

luci-app-audiowrt
  -> authenticated appliance status
```

This separation lets the same packages be installed on a standard OpenWrt system independently from the AudioWRT distribution build.

## First-boot network state

On an unprovisioned device:

1. OpenWrt's board-specific network topology is retained.
2. The normal `lan` interface is changed from router-side static addressing to DHCP client mode.
3. DHCP serving on the normal LAN is disabled.
4. If Wi-Fi is available, the first radio is used to create `AudioWRT-XXXX`.
5. The setup AP is isolated and attached to a dedicated `192.168.77.0/24` setup network.
6. DNS is temporarily redirected to the local setup address.
7. uhttpd serves the AudioWRT setup page.
8. IPv4 and IPv6 forwarding are disabled because AudioWRT is not a router.

Submitting Wi-Fi credentials temporarily disables the setup AP and creates a STA interface. A successful DHCP-up state marks the device provisioned. A failed attempt restores the setup AP.

Once provisioned, ordinary Wi-Fi loss does not reopen the setup AP. A long WPS-button press explicitly re-enters provisioning mode where supported.

There is no Internet forwarding from the setup AP and no normal NAT/router role.

## Audio state

The runtime output manager looks for a USB Audio card with a playback PCM. When one is found it creates `/etc/asound.conf` with a shared ALSA `default` output and records the selected card in UCI.

MPD and AirPlay both consume that logical ALSA output rather than hard-coding a board or card number.

If the USB device changes, hotplug processing reruns output discovery and restarts the audio services.

## Filesystem overlay

The distribution-level `files/` directory is copied into OpenWrt's root filesystem overlay before compilation.

It is intentionally limited to image identity and distribution-only files such as the login banner. Network provisioning and audio services live in reusable packages instead.

## Package feed

`audiowrt-packages` is added as an OpenWrt feed during every build.

The build accepts `AUDIOWRT_PACKAGES_REF`, allowing a package branch or tag to be tested independently from the distribution branch. The resolved package-feed commit is recorded in every output manifest.

## OpenWrt version model

OpenWrt versions are build inputs rather than AudioWRT branches.

`OPENWRT_REF=stable` resolves to the latest final upstream release tag. An explicit branch, tag or commit can be supplied for testing or maintenance.

Every output includes a manifest recording the exact OpenWrt commit, AudioWRT commit and AudioWRT package-feed commit used by the build.
