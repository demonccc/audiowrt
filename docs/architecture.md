# AudioWRT Architecture

## Overview

AudioWRT is a reproducible downstream build definition, not an OpenWrt fork. OpenWrt is cloned at build time and remains the source of truth for hardware support. Reusable runtime behavior is implemented in `audiowrt-packages`.

```text
AudioWRT build inputs
  PLATFORM
  OPENWRT_REF
  AUDIOWRT_PACKAGES_REF
  FEATURES (optional)
        |
        v
Clean OpenWrt checkout
        |
        v
OpenWrt device profile
        |
        + hardware-specific packages from OpenWrt
        + AudioWRT core
        + selected optional features
        - generic router packages
        v
AudioWRT firmware
```

## Platform ownership

AudioWRT does not maintain a platform database. `PLATFORM` is the OpenWrt device-profile identifier supplied at build time. Device trees, board definitions, Wi-Fi firmware, Ethernet/switch drivers and USB host-controller packages stay owned by OpenWrt.

The TP-Link TL-WDR4300 v1 (`tplink_tl-wdr4300-v1`) is the initial reference target, not a special-case platform definition.

## USB capability gate

USB host capability is mandatory. The validator runs before AudioWRT package selection and examines the selected profile packages generated by the exact OpenWrt ref being built.

```text
USB confirmed -> continue
USB missing   -> fail
USB unknown   -> fail
```

This prevents AudioWRT's own `kmod-usb-audio` dependency from creating a false positive on hardware with no proven USB host interface.

## Core and optional features

The effective image policy is:

```text
OpenWrt device defaults
+ OpenWrt device packages
+ config/packages.add
+ packages resolved from config/features.map
- config/packages.remove
```

`config/packages.add` is deliberately limited to the appliance core. MPD and AirPlay are optional feature packages and are not part of a default low-flash build.

OpenWrt's normal image-size check is authoritative. A build with requested features fails if the image exceeds the selected device's limit.

## Runtime package architecture

```text
audiowrt-core
  -> identity
  -> Ethernet DHCP client
  -> temporary Wi-Fi setup AP
  -> STA provisioning and rollback
  -> WPS recovery
  -> forwarding disabled

audiowrt-usb-audio
  -> kmod-usb-audio
  -> ALSA default output
  -> USB hotplug

audiowrt-storage
  -> optional ext4 USB extension storage
  -> OpenWrt extroot writable overlay
  -> internal-core fallback
  -> best-effort core-config synchronization

audiowrt-extensions
  -> runtime extension catalog
  -> apk installation from OpenWrt repositories
  -> AudioWRT configuration hooks

audiowrt-mpd / audiowrt-airplay
  -> build-time wrappers around the same runtime integration hooks

luci-app-audiowrt
  -> overview
  -> storage management
  -> extension management
```

## Storage model

The internal flash always contains an AudioWRT core image. External USB storage is optional.

When extension storage is enabled, AudioWRT formats an explicitly selected partition as ext4 and configures it as OpenWrt extroot. After reboot, the external filesystem becomes the writable overlay, so `apk` installs larger packages there without any special package-path logic.

Removing the external device causes OpenWrt to boot using the internal overlay again. While extroot is active, AudioWRT synchronizes critical network and appliance configuration to `/rwm` when OpenWrt can expose the internal overlay there.

The storage manager never formats a disk implicitly. The CLI requires `--yes`, and the LuCI page presents a destructive-operation confirmation.

Runtime write amplification is intentionally limited. MPD database, playlists and state are placed under `/tmp`; application logs use the normal RAM-backed OpenWrt logging path.

## Extensions

The initial runtime catalog contains only integrations with working OpenWrt packages:

- `mpd` -> `mpd-mini`
- `airplay` -> `shairport-sync-mini`

On internal flash these are installed only when sufficient space exists. With external extension storage active, the same `apk add` operation writes to the external overlay transparently.

Spotify Connect is not exposed until AudioWRT has a maintained binary package path for `librespot`.

## First-boot network state

1. OpenWrt's board-specific Ethernet topology is retained.
2. The normal LAN interface becomes a DHCP client.
3. DHCP serving on normal LAN is disabled.
4. The first available Wi-Fi radio creates `AudioWRT-XXXX` for provisioning.
5. The setup AP uses an isolated `192.168.77.0/24` network and temporary wildcard DNS to the local setup page.
6. Submitting valid credentials moves the device to Wi-Fi STA mode.
7. Failed connection attempts restore the setup AP.
8. After provisioning, the setup AP reopens only through explicit recovery.

There is no normal NAT/router role and IPv4/IPv6 forwarding is disabled.

## Build reproducibility

Every build records:

- exact AudioWRT commit;
- exact OpenWrt ref and commit;
- exact `audiowrt-packages` ref and commit;
- resolved OpenWrt platform metadata;
- selected optional features;
- final `.config` and package metadata;
- firmware image-size report.

OpenWrt versions are build inputs rather than AudioWRT branches.

## CI policy

GitHub Actions are manual-only. No workflow is triggered by push or pull request events. The same `make build` command is used locally and by the manually dispatched firmware workflow.
